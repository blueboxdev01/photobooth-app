# v0.9.0 — The guest leaves with a QR code

**Download `photobooth-v0.9.0-win-x64.zip`, unzip, run `Photobooth.Server.exe`.**
Nothing to install — no .NET, no Node.

Then open <http://localhost:5000/operator>.

The test sheet is **[docs/FIELD-TEST.md](../FIELD-TEST.md)**, also in the ZIP, and
is unchanged from v0.8.0 — if you have already run tests 1–7 there is nothing new
to repeat.

## New since v0.8.0

### Google Drive delivery, and the QR

Each finished session becomes **its own Google Drive folder**, shared by link,
and the guest screen shows a QR pointing at it. They scan it and get their own
photos — there is no gallery, and no id to edit to reach anyone else's session.

> **This is off in your build, and stays off.** With no Google account configured
> nothing is uploaded, the guest screen says to ask for the photos, and you need
> no Google account and no internet connection for any test in the field sheet.
> Turning it on is [docs/DRIVE-SETUP.md](../DRIVE-SETUP.md), and it is a decision
> made per machine.

**The guest never waits on the network.** The strip is composed and everything is
written to disk *before* an upload is attempted, so a venue with no signal costs
a guest their QR code and nothing else. Uploads run in the background and retry
with a widening gap; a session that never uploaded can be published from Setup
days later.

**The QR appears before the upload finishes.** The strip goes up first and the
link is published the moment it lands, while the raw photos — which are most of
the ~25 MB — are still going. Waiting for the whole session would routinely put
the code on screen after the guest had walked away.

Failures are told apart, because retrying does not fix them equally:

| | |
|---|---|
| Network dropped | Retried, with a widening gap, until it goes |
| Sign-in revoked or expired | **Not** retried — a red banner on the operator screen says to press Re-authorise |
| Account out of storage | **Not** retried — says so plainly, because retrying makes it no better |

**Setup → Guest delivery** shows whether uploading is on, which account is signed
in, how many sessions are waiting, and anything that gave up — with a **Try
again** button per session.

### The version number is now correct

**v0.8.0 reported itself as `0.7.0`.** The number lived in the project file, the
release pipeline never overrode it, and it was never bumped — so the version
string at the foot of the rail, which the field sheet asks you to quote with
every result, named the wrong release. Releases now take their version from the
tag, so the two cannot drift again.

If you have been quoting `0.7.0` from a build downloaded after v0.7.0, that is
why. This one really is 0.9.0.

## Still true

- **The app cannot fire the shutter.** The countdown is advisory: the guest sees
  "3-2-1" and you press the remote.
- **Everything about the camera is still an assumption.** File naming,
  extensions, timings — none of it has met a real R50. Contradicting it is the
  point of the exercise.

## The one thing we most need to know

**Does the BR-E1 remote work while the camera is USB-tethered?** Canon's own
advice is to disable Bluetooth before connecting USB, which is the opposite of
what the remote needs. Test 1 covers it. If they conflict, the fallback is the
camera's own shutter button and nothing else in the design changes.

## Upgrading from v0.8.0

Unzip alongside the old folder rather than over it, then copy across:

- `data/` — past sessions, your settings and any backdrop image
- `templates/` — any frame you made in the editor

Both live next to the .exe, so a fresh unzip will not have them.

Sessions from older builds are untouched. They are simply marked as never having
been uploaded, which is correct, and can be published later if you ever turn
delivery on.

## Sending results back

**Setup → Download diagnostics bundle.** Logs, every ingest decision with its
reason, the effective settings, and the exact commit. **It contains no
photographs**, and no credentials — anything that looks like a client id, secret
or token is redacted before the file is written.

## Notes

- Windows SmartScreen will warn about an unsigned binary. *More info → Run anyway*.
- You need a **DR-E18 / LP-E17 dummy battery**: the R50 will not power itself over
  USB-C while tethered.
- The version string is at the foot of the left-hand rail; include it with any
  result.
- 148 automated tests pass. None of them involve a camera — that is what the
  field test is for.
