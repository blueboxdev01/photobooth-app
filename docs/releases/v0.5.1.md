# v0.5.1 — Field-test build

The first build meant to leave the development machine. **Download
`photobooth-v0.5.1-win-x64.zip`, unzip, run `Photobooth.Server.exe`.** Nothing to
install — no .NET, no Node, no toolchain.

Then open <http://localhost:5000/operator>.

## Fixed since v0.5.0

**v0.5.0 could not run a session without a camera** — its `samples` folder
shipped empty, so every simulated shutter press failed. Worse, the operator page
threw away the error that said exactly why, so it looked like nothing happened at
all. Both fixed, and CI now starts the published build and fires a mock press
before a release can be created, so a build that cannot run cannot ship.

Also fixed:

- The posing mirror now runs on the **attract screen**, not only during a
  countdown. Guests seeing themselves is what draws them in, and it lets you
  check framing without starting a session.
- Camera failures now say what to do. "Could not start video source" is reported
  as **"The camera is busy"** with the usual culprits listed and a *Try again*
  button — it almost always means another tab or another app holds the device.
- The diagnostics page no longer opens the camera just to read device labels,
  which was itself competing with `/display` for it.

## Please read this first

Everything in this build about how the camera behaves is an **assumption**. The
app has been written and tested entirely without a Canon EOS R50 in the room. The
file naming, the extensions, how long a transfer takes, whether the Bluetooth
remote even works while tethered — all guesses.

So contradicting it is the point. **A "that's wrong" is a more useful result than
a pass.** Every one of those assumptions is configuration rather than code, so a
correction is a settings change and not a rewrite.

The test sheet is **[docs/FIELD-TEST.md](../FIELD-TEST.md)**, also included in the
ZIP.

## What this build does

- Watches the folder EOS Utility saves into and picks up photos as they land
- Runs a three-shot session: countdown → capture → review, with retake and abort
- Shows a guest screen with a live posing mirror from a **separate webcam**
- Reports on itself at `/diagnostics`

## What it deliberately does not do

- **No uploading.** Google Drive is not in this build, so there is no account to
  set up and no credentials to share. Photos stay in the `data` folder beside the
  .exe.
- **No strip compositing yet.** That is the next milestone, and the layout is
  better tuned once we know what real photos look like.
- **No printing.**

## The two cameras

They are entirely separate paths, and it is worth being clear which is which:

| | Capture | Preview |
|---|---|---|
| Device | Canon EOS R50 | any webcam |
| Reaches the app as | JPEGs in a watch folder | a browser video stream |
| Fired by | the BR-E1 remote, or the camera's own button | n/a |
| Can the app trigger it? | **No** | n/a |

The app cannot fire the shutter. That is a deliberate consequence of using EOS
Utility instead of Canon's developer SDK, and it means the countdown is
**advisory** — the guest sees "3-2-1" and you press the remote, and the two can
drift apart. Please tell us whether that feels acceptable in practice.

## The one thing we most need to know

**Does the BR-E1 remote work while the camera is USB-tethered?**

Canon's own tethering advice is to disable Bluetooth *before* connecting USB,
which is the opposite of what the remote needs. We could not determine whether
they coexist. Test 1 on the sheet covers it. If they conflict, the fallback is
the camera's own shutter button and nothing else in the design changes.

## Sending results back

`/diagnostics` → **Download diagnostics bundle**. It contains the logs, every
ingest decision with the reason for it, the settings this build ran with, and the
exact commit.

**It contains no photographs.** File names and sizes appear in the log; the images
themselves stay on your machine. If a particular photo matters, send that one
deliberately.

## Notes

- Windows SmartScreen will warn about an unsigned binary. *More info → Run anyway*.
- You need a **DR-E18 / LP-E17 dummy battery**: the R50 will not power itself over
  USB-C while tethered, and a real battery lasts well under an hour in a booth.
- The version string at the top of `/diagnostics` identifies the exact commit —
  please include it with any result.
