# v0.8.0 — Rearrange the shots, backdrop templates, a console that fits a phone

**Download `photobooth-v0.8.0-win-x64.zip`, unzip, run `Photobooth.Server.exe`.**
Nothing to install — no .NET, no Node.

Then open <http://localhost:5000/operator>.

The test sheet is **[docs/FIELD-TEST.md](../FIELD-TEST.md)**, also in the ZIP. It
has a new **Test 7** for the reordering below; everything else is unchanged, so
if you have already run tests 1–6 you do not need to run them again.

## New since v0.7.0

### You decide which shot goes in which slot

The guest posed six times and one of those is the good one. Which shot opens the
strip is a judgement the software should not be making, so it no longer does.

Run a session, and while the console says **All shots are in** — before you press
Accept — every thumbnail can be moved: drag it, or use the `‹` `›` arrows on it.
**Back to capture order** undoes the lot.

The order decides everything downstream, not just the preview:

| | |
|---|---|
| The strip | composited in the order you arranged |
| The raw photos | `photo-1.jpg` is whichever shot you put first |
| The guest screen | follows along as you move things |

That second row is the point. The guest's loose photos are numbered to match the
strip they are holding, rather than to match the order the shutter happened to
fire in.

Each thumbnail keeps its **capture number**, so a photo dragged to the front is
still labelled "shot 4" and you can talk about it with the guest standing next to
you.

> **Retake still means the shot you took last**, whatever position you have moved
> it to — otherwise dragging a photo to the end would quietly change which one
> Retake throws away. Its replacement comes back into the same slot, so one
> retake does not cost you the arrangement.

Rearranging is only possible during review. Before that the set is incomplete;
after Accept the strip is already being built.

### Template art can be a backdrop, not just a frame

Uploading a decorative image used to hide the photos behind it. Art is now drawn
**behind or in front depending on what it is**, and which one it is gets detected
from the image itself:

| | |
|---|---|
| **Backdrop** | Opaque where the photos go. Drawn underneath them. **PNG or JPEG** |
| **Frame** | Transparent where the photos go. Drawn over them, showing them through its windows. PNG only |

It judges by transparency **inside the photo slots** rather than overall, so a
frame with a wide solid border is still correctly read as a frame. The editor
shows what it decided and has a one-click override if it ever guesses wrong.

Art that is the wrong shape is now **scaled to fill and centre-cropped** instead
of stretched, so faces and lettering are never distorted — but the edges get
trimmed. The editor states the exact pixel size to upload, next to the upload
button:

| Output size | Pixels (all at 300 DPI) |
|---|---|
| Photo strip 2×6 | 600 × 1800 |
| Portrait 4×6 | 1200 × 1800 |
| Portrait 5×7 | 1500 × 2100 |
| Landscape 6×4 | 1800 × 1200 |
| Landscape 7×5 | 2100 × 1500 |

### Slot sizes you can type

**Templates → Slot position** now takes X, Y, **width and height** in pixels. A
drag cannot land on an exact size, and photos at different sizes on one strip
read as a mistake, so there is also **Make every slot this size** — it copies the
selected slot's dimensions to all the others without moving them.

The slot list shows each slot's size, so a mismatch is visible at a glance.

### The console works on a phone

The left rail becomes a header on a tablet and everything goes single-column on a
phone, with touch-sized targets. Not because a booth is run from a phone, but
because you will want to check a setting on one.

The template editor is also properly three columns again on a desktop — canvas,
controls, render preview — instead of stacking them.

### Smaller things

- The **ingest decisions** log on the Setup page is collapsed behind a summary
  with its counts. It is still there, and still in the diagnostics bundle — it
  was just burying the settings.
- Buttons, dropdowns and file pickers look the same everywhere now.

## Still true

- **No uploading.** Google Drive is not in this build. Photos stay in the output
  folder on your machine.
- **The app cannot fire the shutter.** The countdown is advisory: the guest sees
  "3-2-1" and you press the remote.
- **Everything about the camera is still an assumption.** File naming,
  extensions, timings — none of it has met a real R50. Contradicting it is the
  point of the exercise.

## The one thing we most need to know

**Does the BR-E1 remote work while the camera is USB-tethered?** Canon's own
advice is to disable Bluetooth before connecting USB, which is the opposite of
what the remote needs. Test 1 covers it. If they conflict, the fallback is the
camera's own shutter button and nothing else in the design changes.

## Upgrading from v0.7.0

Unzip alongside the old folder rather than over it, then copy across:

- `data/` — past sessions, your settings and any backdrop image
- `templates/` — any frame you made in the editor

Both live next to the .exe, so a fresh unzip will not have them.

Templates made in v0.7.0 keep working and are treated as frames, which is what
they were. Re-upload the art if you meant it as a backdrop.

## Sending results back

**Setup → Download diagnostics bundle.** Logs, every ingest decision with its
reason, the effective settings, and the exact commit. **It contains no
photographs** — if a particular photo matters, send that one deliberately.

## Notes

- Windows SmartScreen will warn about an unsigned binary. *More info → Run anyway*.
- You need a **DR-E18 / LP-E17 dummy battery**: the R50 will not power itself over
  USB-C while tethered.
- The version string is at the foot of the left-hand rail; include it with any
  result.
- 115 automated tests pass. None of them involve a camera — that is what the
  field test is for.
