# v0.6.0 — Strips, templates and booth setup

**Download `photobooth-v0.6.0-win-x64.zip`, unzip, run `Photobooth.Server.exe`.**
Nothing to install — no .NET, no Node.

Then open <http://localhost:5000/operator>.

The test sheet is **[docs/FIELD-TEST.md](../FIELD-TEST.md)**, also in the ZIP.
It has been updated: setup is simpler than it was in v0.5.1.

## New since v0.5.1

### Set the watch folder in the app

Previously you had to make EOS Utility save to a folder the app had been
compiled to expect. Now it works the other way round: note wherever EOS Utility
already saves, and paste it into **Setup** on the diagnostics page.

**Check folder** tells you whether the path is usable *before* you commit to it —
a missing drive letter or a folder Windows will refuse is reported as such,
rather than accepted and then failing. **Save and apply** re-points the watcher
immediately, with no restart, and the choice persists.

The countdown and the no-photo timeout are set there too. Please set the timeout
from the press-to-file latency you measure — 20 seconds is a guess.

### Sessions produce a strip

Accepting a session now composites the photos into a **2×6 strip at 300 DPI** and
writes everything to `data/sessions/<name>/`:

```
strip.jpg   photo-1.jpg   photo-2.jpg   photo-3.jpg   session.json
```

The originals stay in the watch folder, untouched — the app copies, never moves,
because that folder belongs to EOS Utility.

The strip carries its physical size in the file, so it prints as 2×6 inches
rather than at whatever size a print dialog guesses.

### A template editor

`/templates` lets you upload frame art as a PNG and drag the photo slots over it,
with sample photos in place so you can see what the crop does. **Render preview**
builds a strip through the same code a real session uses, so what you see is what
you get.

**The slot count is the shot count.** A four-slot template makes sessions take
four photos, with nothing else to change.

If the strip layout is wrong when you see it on real faces, you can fix it
yourself and tell us what you changed.

## Still true

- **No uploading.** Google Drive is not in this build. Photos stay in the `data`
  folder beside the .exe.
- **The app cannot fire the shutter.** The countdown is advisory: the guest sees
  "3-2-1" and you press the remote. Please say whether that feels acceptable.
- **Everything about the camera is still an assumption.** File naming,
  extensions, timings — none of it has met a real R50. Contradicting it is the
  point.

## The one thing we most need to know

**Does the BR-E1 remote work while the camera is USB-tethered?** Canon's own
tethering advice is to disable Bluetooth before connecting USB, which is the
opposite of what the remote needs. Test 1 covers it. If they conflict, the
fallback is the camera's own shutter button and nothing else in the design
changes.

## Upgrading from v0.5.1

Unzip alongside the old folder rather than over it, then copy across:

- `data/` — past sessions and your saved settings
- `templates/` — any frame you made in the editor

Both live next to the .exe, so a fresh unzip will not have them.

## Sending results back

`/diagnostics` → **Download diagnostics bundle**. Logs, every ingest decision
with its reason, the effective settings, and the exact commit.

**It contains no photographs.** If a particular photo matters — a badly cropped
strip, say — send that one deliberately.

## Notes

- Windows SmartScreen will warn about an unsigned binary. *More info → Run anyway*.
- You need a **DR-E18 / LP-E17 dummy battery**: the R50 will not power itself over
  USB-C while tethered.
- Include the version string from the top of `/diagnostics` with any result.
